# Call Me Maybe

## Description

**Call Me Maybe** is a function-calling engine that uses a small language model to translate natural-language requests into structured JSON function calls.

Given a set of available function definitions and a natural-language prompt, the program asks the LLM to select the most appropriate function and generate all of its required parameters with the correct types.

## Instructions

The project requires:

-   Python 3.10 or later.
-   `uv`.
-   The provided `llm_sdk` package containing Qwen/Qwen3-0.6B.

### Input Files

#### Function definitions

`functions_definition.json` contains the functions that the LLM is allowed to call.

Each function contains:

-   `name`
    
-   `description`
    
-   `parameters`
    
-   `returns`
    

For example:

```json
{
  "name": "fn_add_numbers",
  "description": "Add two numbers together and return their sum.",
  "parameters": {
    "a": {
      "type": "number"
    },
    "b": {
      "type": "number"
    }
  },
  "returns": {
    "type": "number"
  }
}

```

The definitions are validated using Pydantic models before generation starts.

#### Function-calling prompts

`function_calling_tests.json` contains the natural-language requests:

```json
[
  {
    "prompt": "What is the sum of 2 and 3?"
  },
  {
    "prompt": "Reverse the string 'hello'"
  }
]

```

## Algorithm
The core of the function calling engine lays in **constrained decoding.**
It begins with encoding the whole functions file and appending the expected initial **JSON** structure to give enough context to the LLM. 

The generation loop goes like this:
`Get Logits from Input IDs` → `Apply Constrained Decoding` → `Select Highest Probability Value` → `Append the Selected Token to Input IDs`

**Constrained decoding** controls what tokens are valid to ensure proper **JSON** structure.
When a function name has to be generated, all tokens that can form a name are evaluated until one of the function names gets picked:

It may start with `fn_`
There may be possibilities like:
* print
* greet
* input

And the model predicts what tokens are more likely based on the context.
Once a function name is selected, the parameters structure is injected one at a time into the input IDs.
Each parameter type gets its own allowed tokens, for example numbers can only contain number tokens and booleans can only contain the `true` and `false` tokens.

So basically, all the structure is manually injected, and the rest is generated by the model.

## Design Decisions

### Separation of responsibilities

The project is split into several components with distinct responsibilities:

* `validation.py` defines and validates the data structures.
* `json_parser.py` handles input and output JSON files.
* `base_prompt.py` builds the prompt containing the available functions.
* `decoder.py` implements constrained decoding and generation state.
* `engine.py` manages the LLM and generation loop.
* `__main__.py` handles command-line execution and high-level orchestration.

## Performance
This implementation relies on injecting the necessary structure manually and then letting the model decide what to put on the parameters or what function to use, so the performance really depends on the hardware of the machine it's being used on.

## Challenges

### String escaping

The most hard thing to accomplish was without a doubt implementing a safe way to generate characters with a preceding backslash when generating regex (`\\d+`).
To solve this, when the model picked a token with a backslash, the next token had to be checked, and if it didn't contain a backslash at the start, then all logits had to be set to -infinite with constrained decoding except for the single token that just contains a backslash.

## Testing Strategy
To ensure proper **JSON** output generation, multiple tests were created to debug specific edge cases and undesired situations.

These are the things that are tested:
* Proper parameter type generation
* Trailing commas
* Backslash before other characters
* Floating points

Some of the tests rely on tricking the model into doing things it wouldn't normally do, like adding extra decimal points (`1.2.3`) or adding trailing commas by making it think there's three parameters when there's actually just two.
